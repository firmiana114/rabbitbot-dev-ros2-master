# DOCX严格剧本workflow逻辑

本文档记录当前 `workflow` 中 DOCX 严格剧本模式的执行逻辑，用于现场联调、非联调排练和后续维护。

## 运行模式

当前默认启用 DOCX 严格剧本模式：

```bash
RABBITBOT_STRICT_DOCX_SCRIPT=1
RABBITBOT_SCRIPTED_TOUR=1
```

非联调脚本会额外开启：

```bash
RABBITBOT_WORKFLOW_NON_INTEGRATION=1
```

非联调模式只影响导航确认：需要机器人到某个点位时，终端按任意键即视为到达成功。动作、TTS、STT、Memory Agent、Robot Agent 仍按真实服务链路执行。

## 总体原则

当前目标是保证 DOCX 主流程完整、稳定、可预测地跑完，因此严格剧本模式遵循：

- 开场问答：允许 STT 输入。
- 开场非问答播报：不允许普通打断进入 planner/chat。
- 咖啡询问：允许 STT 输入。
- 机器狗表演确认：允许 STT 输入。
- 导航确认：非联调按键确认，联调时等待 body/RobotAgent 导航结果。
- 剧本讲解：不允许普通打断进入 planner/chat。
- 停止词：保留停止当前播报的能力。
- 剧本结束：结束 DOCX 剧本推进，切换到剧本后普通聊天模式。

当前没有按 DOCX 表格中的 `15s`、`30s`、`180s` 等时长做强制等待。流程按“到点确认 -> 播完台词 -> 进入下一阶段”的事件顺序推进，避免时间限制影响剧本完整跑完。

## 主流程顺序

当前 DOCX 剧本流程为：

```text
点位1 起始板块：开场问答
-> 点位2 多功能展示区：跟随步行、点咖啡
-> 点位3 园区历史板块：初步介绍、机器狗表演、拿取咖啡
-> 点位4 园区布局板块：观看沙盘
-> 点位5 合影板块：告别并指引小巴方向
-> 剧本完成
-> 进入剧本后普通聊天模式
```

## 需要接收用户说话的阶段

严格剧本模式中，真正需要用户回答并影响流程的地方只有四类。

### 1. 开场问称呼

位置：点位1 / 起始板块。

机器人播报：

```text
领导，您怎么称呼？
```

等待时间：`8s`。

期望输入示例：

```text
我姓张
张总
王主任
李经理
```

处理逻辑：

- 能识别称呼时，后续用识别出的称呼替换剧本中的 `A+职位简称`。
- 超时或识别不到有效称呼时，默认使用 `领导`。

开场中其他铺垫台词，例如“各位领导都到齐了吗？”、“请问哪位是领导？”、“请把话筒给领导。”、“那您随我来，我简单的给您介绍一下园区。”，在严格 DOCX 剧本模式下不会把普通 STT 识别结果作为用户打断送入 planner/chat。

### 2. 开场问是否第一次来

位置：点位1 / 起始板块。

机器人播报：

```text
领导，欢迎您来到我们人形机器人产业园，您是第一次来我们园区吗？
```

等待时间：`8s`。

如果无法判断，会重问：

```text
我没听清，您是第一次来我们园区吗？
```

重问等待时间：`8s`。

期望输入示例：

```text
是的
第一次
不是
来过
以前来过
```

处理逻辑：

- 判断为第一次来：播报“那您随我来，我简单的给您介绍一下园区。”
- 判断为不是第一次来：播报“那之前您来的时候，我还没来，我们园区最近做了一些升级，您随我来，我简单的给您介绍一下。”
- 两次都无法判断时，默认按第一次来处理。

### 3. 点咖啡

位置：点位2 / 多功能展示区。

机器人播报：

```text
对了，领导、各位，我们这里有咖啡，拿铁、美式，您看您各位需要什么？
```

等待时间：`8s`。

期望输入示例：

```text
拿铁
美式
都可以
不用了
不喝咖啡
```

处理逻辑：

- 只接受咖啡相关回答，例如 `拿铁`、`美式`、`咖啡`、`都可以`、`不用了`、`不喝咖啡`。
- 收到咖啡相关回答时，记录到 `coffee_order`。
- 收到无关文本时，打印“忽略非咖啡相关回答：xxx”，并按未收到有效咖啡选择继续流程。
- 当前版本只记录，不联动咖啡吧、送餐机器人或后续台词分支。
- 超时后直接继续，说“好的，我来给各位安排。”

### 4. 确认观看机器狗表演

位置：点位3 / 园区历史板块。

机器人播报：

```text
领导，您的到来我和我的小伙伴们都非常高兴，他们说要给您表演个节目，您看咱们看个节目，顺便等下咖啡？
```

等待时间：`8s`。

期望输入示例：

```text
是的
好
好的
可以
看吧
没问题
```

处理逻辑：

- 只接受观看表演相关的确认回答，例如 `是的`、`好`、`可以`、`看吧`、`没问题`。
- 收到确认回答时，记录到 `dog_show_confirmation`，然后继续说“小伙伴们动起来吧！”。
- 收到无关文本时，打印“忽略非机器狗表演确认回答：xxx”，并按未收到有效确认继续流程。
- 超时后默认继续，避免现场无人回答时卡住剧本。

## 剧本讲解期间的输入处理

除上述结构化输入阶段外，其他剧本讲解阶段虽然会启动监听线程，但不会等待用户说话，也不会让普通输入进入 planner/chat。

讲解期间的处理规则：

```text
好的 / 继续吧 / 嗯 / 可以 / 收到 / 明白了
-> 忽略并继续播报

其他普通话语
-> 打印“严格演出模式忽略剧本讲解输入：xxx”
-> 继续播报

停止 / 停
-> 保留停止当前播报的能力
```

因此在严格剧本模式下，类似“我不喝咖啡”“这个沙盘很大”“机器狗挺有意思”等话语不会进入普通聊天，也不会触发导航 planner。

## 剧本结束后的普通聊天模式

DOCX 剧本全部完成后，workflow 不再直接退出，而是进入剧本后普通聊天模式。

该模式的行为：

- 不再推进 DOCX 剧本。
- 不再使用导览阶段的 planner 分流。
- 不再主动询问用户想去哪个展示板块。
- 用户后续输入会直接进入剧本后普通聊天 agent。
- 剧本后普通聊天 prompt 不强调展厅导览任务，允许回答简单数学、常识、日常聊天和现场寒暄。
- 普通聊天仍不具备实时联网能力；实时新闻、股票、赛事比分等问题会说明无法确认。

因此，剧本结束后用户可以继续问：

```text
一加一等于几？
你还能聊天吗？
刚才表现不错
上海今天适合散步吗？
```

这些问题会按普通聊天处理，不再回到导览阶段的“您对哪个板块感兴趣”逻辑。

## 点位与阶段

### 点位1：起始板块

阶段：步入展厅、开场问答。

当前动作：

- `握手`：对应剧本“伸手-握手-收手”。执行后等待 `3s`，再追加 `release arm` 收回胳膊，并等待收回后再继续讲话。
- `打招呼`：对应剧本“手部轻微挥手/欢迎”。执行后会追加 `release arm` 收回胳膊，并等待收回后再继续讲话。

当前不会导航到起始板块。严格 DOCX 剧本默认机器人已经站在点位1。

### 点位2：多功能展示区

阶段：跟随步行、点咖啡。

导航：

- 从点位1到点位2。
- 非联调模式下，终端按任意键确认到达。

当前动作：

- `OK手势`：对应剧本“好的，我来给各位安排”时的单手 OK。执行后会追加 `release arm` 收回胳膊，并等待收回后再继续讲话。

### 点位3：园区历史板块

阶段：初步介绍、机器狗表演、拿取咖啡。

导航：

- 从点位2到点位3。
- 非联调模式下，终端按任意键确认到达。

当前动作：

- `right_hand_pointing`：对应指向机器狗方向。
- `right_hand_pointing`：对应指向送咖啡机器人方向。

当前不会真实联动机器狗表演，也不会真实联动送餐机器人送咖啡。

### 点位4：园区布局板块

阶段：观看沙盘。

导航：

- 从点位3到点位4。
- 非联调模式下，终端按任意键确认到达。

当前动作：

- `right_hand_pointing`：对应手指向沙盘方向。

### 点位5：合影板块

阶段：告别并指引小巴方向。

导航：

- 从点位4到点位5。
- 非联调模式下，终端按任意键确认到达。

当前动作：

- `right_hand_pointing`：对应手指向北门门口、小巴方向。
- `再见`：对应挥手告别。执行后会追加 `release arm` 收回胳膊，并等待收回后再继续讲话。

当前不会真实联动小巴开门或接人。

## 动作指令链路

非联调模式不会绕过动作。当前动作仍会通过以下链路发送：

```text
workflow
-> RobotAgent /do_arm_async
-> NaviArmActionClient
-> body action server
```

RobotAgent 日志中出现以下内容且 HTTP 为 `200 OK`，说明动作请求已经发到 RobotAgent 并进入 body action client：

```text
Do arm: 动作名
NaviArmActionClient: action_name 动作名
POST /do_arm_async HTTP/1.1" 200 OK
```

当前 DOCX 剧本使用的动作名：

```text
握手
打招呼
OK手势
right_hand_pointing
再见
release arm
```

当前明确不使用 body 不支持的 `指尖轻点`。

其中 `release arm` 不是 DOCX 独立动作，而是 workflow 在 `握手`、`打招呼`、`OK手势` 和 `再见` 后自动追加的收回动作。默认时序为：先等待一段时间让原动作展开，再发送 `release arm`，再等待 `1.2s` 后开始对应台词。`握手` 的展开等待默认是 `3s`，其他动作默认是 `1.2s`。现场可通过环境变量 `RABBITBOT_HANDSHAKE_BEFORE_RELEASE_DELAY`、`RABBITBOT_ARM_BEFORE_RELEASE_DELAY` 和 `RABBITBOT_ARM_RELEASE_WAIT_SECONDS` 微调。

## 当前动作编排

当前 workflow 中 DOCX 剧本动作只通过 `/do_arm_async` 发送手臂动作。动作与剧本阶段的对应关系如下：

| 剧本位置 | 触发时机 | workflow 动作指令 | 对应 DOCX 动作 |
| --- | --- | --- | --- |
| 点位1 / 开场问答 | 询问称呼后，向领导问好前 | `握手` -> `release arm` | 伸手、握手、收手，然后收回胳膊 |
| 点位1 / 开场问答 | 欢迎领导来园区前 | `打招呼` -> `release arm` | 手部轻微挥手、欢迎，然后收回胳膊 |
| 点位2 / 点咖啡 | 说“好的，我来给各位安排”前 | `OK手势` -> `release arm` | 单手伸出，手势为 OK，然后收回胳膊 |
| 点位3 / 机器狗表演 | 邀请观看机器狗表演前 | `right_hand_pointing` | 手指向机器狗方向 |
| 点位3 / 拿取咖啡 | 提醒咖啡已到、请领导自取前 | `right_hand_pointing` | 手指向送咖啡机器人方向 |
| 点位4 / 观看沙盘 | 沙盘介绍前 | `right_hand_pointing` | 手指向沙盘方向 |
| 点位5 / 告别并指引小巴方向 | 介绍无人驾驶小巴前 | `right_hand_pointing` | 手指向北门门口、小巴方向 |
| 点位5 / 告别并指引小巴方向 | 说“各位领导再会”前 | `再见` -> `release arm` | 挥手告别，然后收回胳膊 |

RobotAgent 日志中如果出现以下序列，说明动作已经从 workflow 发到 RobotAgent 并进入 body action client：

```text
===== do_arm_async =====
Do arm: 动作名
NaviArmActionClient: action_name 动作名
POST /do_arm_async HTTP/1.1" 200 OK
```

注意：`200 OK` 代表 RobotAgent 接收并发送 action 请求成功，不等价于物理动作一定已经完整执行完。若需要确认实体动作完成，需要继续查看 body action server 的完成回执或现场观察。

## 已知未覆盖项

以下内容在 DOCX 中存在，但当前 workflow 尚未实现或不通过 `/do_arm_async` 表达：

- 身体向左右旋转。
- 上前靠近领导一步。
- 站立不动。
- 走跑模式。
- 机器狗真实表演联动。
- 送餐机器人送咖啡联动。
- 小巴开门和接人联动。
- 按 DOCX 表格时长强制等待。

这些项目不影响当前“完整顺利跑完剧本主流程”的目标。

## 常用测试方式

启动非联调 workflow：

```bash
/mnt/ssd/navgation/projects/rabbitbot-dev-ros2-master/scripts_1/start_non_integration_workflow.sh
```

命令行向 STT 注入一句话：

```bash
docker exec navid-vllm-cuda-mic-audio bash -lc \
'curl -sS -X POST http://127.0.0.1:28184/exec \
  --form-string '"'"'task={"task":"inject_text_async","lang":"zh","text":"我是第一次来","timeout":30}'"'"''
```

注意：注入文本必须落在当前 STT 等待窗口内。比如回答“是否第一次来”时，需要在对应 `audio_input early ask: timeout 8` 的 8 秒内注入；如果晚到剧本讲解阶段，会被严格演出模式忽略。
